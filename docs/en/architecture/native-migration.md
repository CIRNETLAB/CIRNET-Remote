# CIRNET migration plan for C++ and Rust

[Tiếng Việt](../../vi/architecture/native-migration.md) · [Original plan dated 2026-11-05](https://github.com/cirnetlab/cirnet-remote/blob/f91eeeb42d7528d4e7fa9b1526195847932faf9d/docs/superpowers/plans/2026-11-05-cirnet-native-migration.md) · [Stage 0 record](../../verification/2026-11-05-native-migration-stage-0.md)

**Recorded status. Gate 0 is incomplete.** The team authenticated and exercised the released 0.1.4 reference set. The report records digest checks for all 15 artifacts, HTTP, SQLite, gRPC and Simulator runs, and 18 passing PostgreSQL cases. The loaded Stop measurement with a worker still running, integrated phase timings, PostgreSQL load profile, paired reference database and capture snapshots, and absolute thresholds are still missing. Stages 1–5 are `NOT RUN`. The combinations and thresholds below are planned acceptance criteria.

> **For implementation agents.** Use superpowers:subagent-driven-development or superpowers:executing-plans. Complete each gate and record its evidence before beginning the next stage.

**Goal.** Preserve compatibility with the released system, then migrate to Interface Vue/TypeScript → Remote Rust → Hardware Rust → Simulator C++.

**Architecture.** Interface keeps REST and WebSocket on the same origin. Remote owns orchestration, data and leases. Hardware owns local RPC, station control and the Simulator process. Contracts supplies schemas, SDKs and canonical data. During stages 1–2, preview continues through the Remote adapter. From stage 3, preview may go through Hardware after that stage's combination passes its gate.

**Tools.** Use C++20 and CMake for the worker, Rust and the Cargo lock for binaries and generators, Node for the TypeScript SDK, and pytest and Playwright Python for acceptance. Lock the compiler, linker, target and dependencies in the candidate manifest before measuring. Choose release versions of the C++ and Rust tools in their corresponding stages.

## Rules for every stage

- Follow the order **0 → 1 → 2 → 3 → 4 → 5**. Each required gate records its command, artifact combination, result and evidence. A required FAIL or NOT RUN blocks both switching the default and starting the next stage.
- Each combination uses released or packaged candidate artifacts identified by commit, version, SHA-256, target and build flags. Use sibling source for development or to export separate artifacts. Distinguish the surveyed HEAD, build revision and harness revision. Raw data and traces go in a session outside Git allocated by the pinned DEV allocator. Keep only Markdown reports in the repository.
- The final product keeps Python in tests and benchmarks. During the transition, keep compatible Python artifacts and all reference tests. PRs run tests near the change and relevant auth and safety checks. Integration gates exercise real processes and artifacts. Release gates run the exact artifacts intended for delivery.
- Use the same valid and invalid fixtures to check wire behavior. Pin both canonical and legacy RPC paths, protobuf presence, REST names, types, statuses and errors, WebSocket sequence and resync, NCAP bytes, ownership and durable data. A breaking change requires a wire version and a separate consumer migration plan.
- Before switching a default, record how to restore the most recent gated combination. Stop admitting Run, wait for safe cleanup or retain quarantine, and keep the matching database and capture backup with the manifest. At startup, the Python scheduler can dispatch `QUEUED` records. Before giving a scheduler permission to call Hardware after cutover or restore, inspect the restored queue and resolve or isolate all pending commands. Check ownership, capture digests, leases, quarantine and that only one scheduler can control Hardware. Check that Start is never replayed after a crash or an uncertain ACK.

- [ ] **Measure the external path.** Run `python -B -m scripts.benchmark_web_sessions --sessions 50 --concurrency 10 --runs 8 --read-rounds 3` as the smoke baseline. Keep the existing AND workload, X at 0 ns, 0 at 8 ns and 1 at 28 ns, and add an event-heavy digital graph and a large NCAP payload from existing fixtures. Pin the input, harness and dependency inventory SHA-256, 50 principals, 10 concurrent HTTP requests, four workers, current auth policy, seed, warmup and measurement window for separate SQLite and PostgreSQL profiles. Calculate throughput as requests completed in the load window divided by seconds in that window. Calculate jobs/s and capture bytes/s separately. Collect CPU seconds per job, peak aggregate RSS for the process tree and sample count. RSS can count shared pages more than once. Separate bootstrap and login pacing from the load window. Collect at least 100 valid observations for each p99 distribution on each run, measure at least three independent runs after warmup, and report the sample count and nearest-rank method. The existing benchmark shares an API/Hardware process and issues Stop after COMPLETE. Use a pytest harness with separate processes for per-service and PostgreSQL measurements.
- [ ] **Measure Stop under load and separate phases.** Extend the pytest harness in `tests/integration/` and reuse `scripts/benchmark_web_sessions.py` for HTTP and resource metrics. Pin the graph and confirm all slots are busy, the worker has started the target job and that job is still running when Stop is issued. Discard the observation if the job finishes first. Measure Stop to HTTP response, gRPC ACK, and safe release or durable quarantine separately. Use natural graph load for timing and separate injected hang, crash and late-ACK cases for invariants. Use a monotonic clock in each process and request/experiment IDs to attribute Remote planning, queue and API time, Hardware graph compile, worker wait, Simulator run, NCAP encode/read/transfer/decode, payload store/read and database waits and transactions. - [x] **Compare core measurements.** Run `python -B -m pytest -q tests/integration/native_baseline_cases.py --basetemp <owned>/pytest-native-baseline` separately, using the verified environment. Use these microbenchmarks to compare against integrated spans.
- [ ] **Lock thresholds before testing a candidate.** The implementer's initial rule allows zero corpus or safety-invariant differences. Compare medians across runs for each identically configured profile. Require p95/p99 and peak RSS ≤ 110% of baseline, CPU/job ≤ 110%, and throughput ≥ 95%. For Stop, use the stricter of the current operational limit and 110% of baseline p95/p99. Keep leases unavailable until safe ACK. Require the C++ Simulator to reduce p95 core run time or CPU/job by at least 10%, with an effect larger than measurement variation across three paired runs, while meeting the other thresholds. If sample size, load or variation is insufficient, finish measuring and record absolute values before evaluating a candidate.
- [ ] **Gate 0.** PASS requires authenticated artifacts, a reference corpus, phase measurements, loaded Stop and locked thresholds. Report using the template at the end.

## Report template for each stage

- Repositories and files changed, commit and harness, artifacts and digests, configuration, environment and commands.
- Combination matrix and PASS/FAIL/NOT RUN for each gate. Report simulation, RTL and HIL on separate rows.
- Sample counts, p50/p95/p99, throughput, CPU/job, RSS and Stop to safe state before and after. Record absolute values, variability and decision thresholds.
- Open failures, conditions for switching defaults, rollback artifacts and backups, and rehearsal outcome.
